### 1. WHY — Research Problem and Motivation
* **Core Problem:** Large language model (LLM) assistants can convert natural language into analysis code, but their responses frequently misinterpret user intent or generate plausible yet erroneous calculations that lead to incorrect conclusions [1, 2].
* **Motivation:** Existing AI interfaces lack verification support, shifting the analyst's cognitive burden from writing code to evaluating AI-generated outputs; without adequate tools, analysts are susceptible to automation bias in high-impact decision environments [2, 3].
  * *Location:* Section 1 "INTRODUCTION", p. 1–2 [1-3].

---

### 2. HOW — Method and Study Design
* **Type of Study:** Qualitative user study using a custom-built interactive "design probe" featuring natural language explanations, code, comments, interactive data tables, and field summary visualizations [4, 5].
* **Sample Size:** 22 professional data analysts (\\(n=22\\)) across diverse roles (data scientists, software engineers, program managers, financial managers) and programming comfort levels [4, 6, 7].
* **Data & Benchmark:** 11 standardized verification tasks (1 tutorial task + 10 main tasks, including 2 error-free control tasks) spanning 9 Kaggle datasets uploaded after February 2022, derived from the ARCADE benchmark [8-10].
* **Databases / LLM Engine:** Tasks utilized natural language prompts and buggy code outputs generated via OpenAI’s Code Interpreter (GPT-4) [9-11].
* **Time Span & Duration:** 60-minute remote video sessions per participant (~10 min tutorial, ~40 min task execution, ~10 min semi-structured interview) [12].
  * *Location:* Section 1 "INTRODUCTION", p. 1; Section 4 "METHOD: DESIGN PROBE AND PREPARED TASKS", p. 3–6; Section 5 "USER STUDY", p. 7; Appendix A "TASK SELECTION PROCESS", p. 15 [4-12].

---

### 3. WHAT — Key Findings, Frameworks, and Typologies
* **Verification Behavior Typology:** Classifies verification into **procedure-oriented** ("what did the AI do?") and **data-oriented** ("does the [resulting] data make sense?") behaviors [13, 14].
* **Behavioral Sequence Pattern:** Analysts typically initiate verification with procedure-oriented behaviors for macro-level comprehension, then pivot to data-oriented behaviors once an anomaly is noticed [13, 15, 16].
* **Interleaved Artifact Framework:** Data artifacts (tables and summary plots) act as secondary support during procedure checks, while procedure artifacts (code and natural language explanations) assist in data sensemaking and provenance tracing [13, 17, 18].
* **Background Influence Model:** Prior coding familiarity inclines analysts toward code auditing, whereas data and domain experience fosters direct data scrutiny and proactive error-hypothesis testing [19-21].
* **Assistant Design Framework:** Proposes four system design imperatives: fluidly connecting data and procedure artifacts, communicating data operation semantics, articulating AI assumptions/interpretations, and embedding AI-guided test cases/checklists [22-25].
  * *Location:* Section 6 "RESULTS", p. 8–11; Section 7.2 "Implications for System Designers", p. 12–13 [13-25].

#### (c) Mechanisms, Conditions, and Antecedents
*   **Conditions Making Verification & Error Detection MORE Likely**:
    *   *Explicit AI Assumptions*: Prompting the AI to state column interpretations and logic assumptions explicitly [9]. *(Section 7.2.3, p. 13)* [9]

*   **Mechanisms Causing Verification FAILURES / Overreliance**:
    *   *Plausibility / Automation Bias*: Plausible-sounding natural language explanations or clean-looking code lead analysts to assume correctness without checking data transformations [6, 46]. *(Section 1, p. 1; Section 6.1.4, p. 9)* [6, 46]
    *   *Lack of Code Literacy*: Inability to read Python code causes non-programmers to rely blindly on summaries or avoid checking intermediate data dicing [47]. *(Section 6.3.2, p. 11)* [47]
